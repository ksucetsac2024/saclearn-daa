Algorithms and how we measure them

Before comparing algorithms we need a ruler. This topic sets up that ruler: what counts as an algorithm, what we measure (time and space), and why one input can be fast while another is slow.

What makes something an algorithm

An algorithm is a finite list of precise steps that turns an input into an output. A recipe that says "add salt to taste" is not quite an algorithm, because "to taste" is not precise. Every algorithm must have these five properties:

Input

Zero or more values supplied from outside.

Output

At least one result. An algorithm that produces nothing is useless.

Definiteness

Each step is clear and has exactly one meaning. "Divide x by 0" or "pick a nice number" fail this.

Finiteness

It stops after a finite number of steps for every input. An infinite loop is not an algorithm.

Effectiveness

Each step is basic enough to be done exactly, by hand with pencil and paper if needed.

Criteria for analysing an algorithm

Once an algorithm is correct, we judge it by:

  • Correctness: gives the right output for every valid input.
  • Time efficiency: how the number of steps grows as the input grows.
  • Space efficiency: how much extra memory it needs.
  • Simplicity and clarity: easier to verify and maintain.
  • Optimality: whether a better algorithm can exist for the problem at all.
Two ways to measure

A priori analysis is done before running: count steps on paper and express them as a function of input size n. It does not depend on the machine. A posteriori analysis (profiling) runs the program and measures actual seconds and bytes, which depend on the computer, compiler and language. This course is about a priori analysis.

Space complexity

Space complexity is the total memory an algorithm needs, written S(P) = c + SP(n):

  • Fixed part c: the code, simple variables and constants. It does not change with n.
  • Variable part SP(n): memory that depends on the input, such as arrays created at run time and the recursion stack.

Iterative factorial

f = 1
for i = 2 to n: f = f * i

Only f, i, n: constant extra space, O(1).

Recursive factorial

Fact(n):
  if n ≤ 1 return 1
  return n * Fact(n − 1)

Fact(n) waits for Fact(n−1), which waits for Fact(n−2)… n frames sit on the stack at once: O(n) space.

Best, worst and average case

For many algorithms the step count depends on which input of size n you give, not just on n. Linear search is the standard example: look at A[1], A[2], … until you find the key.

Best case

The key is at A[1]: 1 comparison. The minimum over all inputs of size n. Θ(1).

Worst case

The key is at A[n] or absent: n comparisons. The maximum over all inputs. Θ(n). This is the guarantee we usually quote.

Average case

The expected count over a probability model of inputs. If the key is present and every position is equally likely: (1+2+…+n)/n = (n+1)/2. Still Θ(n).

Average case recipe

Average = Σ (probability of input type) × (cost for that input type). Pick the probability model first (for example "each position equally likely"), then compute the expected count.

Searching a binary search tree

The same three cases appear in a binary search tree (BST). Searching compares the key with a node and goes left or right, so the cost is the number of nodes on the path.

Best case: the key is at the root, 1 comparison. Worst case: the tree is a straight chain (inserting already-sorted keys creates one), so the search walks all n nodes. In a balanced tree the height is about log₂n, so search is O(log n). Keeping the tree balanced is exactly what AVL trees do (last topic of this module).

The worst case is an upper bound that holds for every input of size n.

Asymptotic notations

Exact step counts like 2n² + 2n + 1 are messy and machine-dependent. Asymptotic notation keeps only how fast a function grows for large n, which is what decides whether an algorithm scales.

The idea: compare growth, ignore constants

For large n, the biggest term dominates. In 3n² + 5n + 100, at n = 1000 the n² term is 3,000,000 while 5n + 100 is only 5,100. So we say the function "grows like n²". Constant multipliers are dropped too, because a faster computer changes them anyway.

Big vs little

Big-O allows equality of growth (n² = O(n²) is true). Little-o forbids it (n² = o(n²) is false, but n = o(n²) is true). The difference is "for some c" versus "for every c".

Worked example: proving a Θ bound with constants

Show f(n) = 3n² + 4n + 7 = Θ(n²).

Upper bound (O)

For n ≥ 1: 4n ≤ 4n² and 7 ≤ 7n². So f(n) ≤ 3n² + 4n² + 7n² = 14n². Take c₂ = 14, n₀ = 1.

Lower bound (Ω)

For n ≥ 1, 4n + 7 > 0, so f(n) ≥ 3n². Take c₁ = 3.

Both hold for n ≥ 1, so 3n² ≤ f(n) ≤ 14n², and f(n) = Θ(n²).

Worked example: disproving a bound

Is n³ = O(n²)? Suppose n³ ≤ c·n² for all n ≥ n₀. Divide by n²: n ≤ c for all n ≥ n₀. But n grows without limit, so no constant c works. False.

Is 3ⁿ = O(2ⁿ)? We would need (3/2)ⁿ ≤ c for all large n, but (3/2)ⁿ → ∞. False. Different exponential bases are different growth rates.

Is log₂(n³) = Θ(log n)? log(n³) = 3 log n, a constant times log n. True. Also log bases do not matter inside O: log₂n = log₁₀n / log₁₀2.

How a property proof goes (transitivity)

f = O(g) gives c₁, n₁ with f(n) ≤ c₁g(n) for n ≥ n₁. g = O(h) gives c₂, n₂ with g(n) ≤ c₂h(n) for n ≥ n₂. For n ≥ max(n₁, n₂): f(n) ≤ c₁g(n) ≤ c₁c₂h(n). So c = c₁c₂ and n₀ = max(n₁, n₂) work. Every property proof follows this pattern: unpack the definitions, chain the inequalities, then name the new constants.

Time complexity of loops

Most "find the complexity of this code" questions reduce to one skill: count how many times the innermost statement runs. Four patterns cover almost everything.

The four patterns

1. Add or subtract a constant

for (i = 1; i <= n; i += 3)

i takes n/3 values: Θ(n).

2. Multiply or divide

for (i = 1; i <= n; i *= 2)

i = 1, 2, 4, …, 2ᵏ ≤ n, so k ≤ log₂n: Θ(log n). Dividing by 2 from n down to 1 is the same.

3. Independent nested loops

for i = 1..n
  for j = 1..m

Multiply: Θ(n·m).

4. Inner loop depends on i

for i = 1..n
  for j = 1..i

Add up the inner count for each i: Σ i = n(n+1)/2 = Θ(n²).

Sums you will need

Σi=1..n 1 = n  ·  Σ i = n(n+1)/2  ·  Σ i² = n(n+1)(2n+1)/6  ·  Σi=0..k 2ⁱ = 2ᵏ⁺¹ − 1

Harmonic: Σi=1..n 1/i ≈ ln n  ·  Σi=1..n log i = log(n!) = Θ(n log n)

Worked examples

Example 1: inner loop shrinks

for (i = 1; i <= n; i++)
    for (j = i; j <= n; j++)
        x++;

For i = 1 the inner loop runs n times, for i = 2 it runs n − 1 times, …, for i = n once. Total = n + (n−1) + … + 1 = n(n+1)/2 = Θ(n²).

Example 2: logarithmic inner loop with base 3

for (i = 1; i <= n; i++)
    for (j = 1; j < n; j = j * 3)
        x++;

The inner loop does j = 1, 3, 9, … < n, which is about log₃n iterations, and it does not depend on i. Total = n · log₃n = Θ(n log n). (The base of the log is a constant factor.)

Example 3: a while loop whose step grows

i = 1; s = 1;
while (s <= n) { i++; s = s + i; }

After k iterations s = 1 + 2 + … + (k+1) ≈ k²/2. The loop stops when k²/2 > n, so k ≈ √(2n): Θ(√n).

Example 4: halving outer loop, linear inner loop

for (i = n; i >= 1; i = i / 2)
    for (j = 1; j <= i; j++)
        x++;

The inner loop runs n, then n/2, n/4, …, 1 times. Total = n(1 + 1/2 + 1/4 + …) < 2n = Θ(n). A geometric series is bounded by a constant times its largest term. Two logarithmic-looking loops do not automatically give n log n.

Common mistakes

Multiplying the two loop counts when the inner loop depends on i (Example 4 is Θ(n), not n log n). Forgetting that j = j * 2 starting from j = 0 never moves (0 × 2 = 0), so such a loop never ends. Treating j += i as linear: Σ n/i = n·Hₙ ≈ n ln n.

Recurrences: iteration and substitution

A recursive algorithm's running time is described by an equation that refers to itself, called a recurrence. Solving it gives a closed form like Θ(n log n).

From code to recurrence

Write T(n) = (cost of the recursive calls) + (cost of the work done in this call).

AlgorithmWhat one call doesRecurrence
Binary searchone call on half the array + one comparisonT(n) = T(n/2) + c
Merge sorttwo calls on halves + merging n elementsT(n) = 2T(n/2) + cn
Recursive factorialone call on n − 1 + one multiplicationT(n) = T(n−1) + c
Towers of Hanoitwo calls on n − 1 disks + one moveT(n) = 2T(n−1) + 1

Every recurrence also needs a base case, such as T(1) = 1. Three solving methods are in the syllabus: iteration, substitution and recursion tree (next topic), plus the Master theorem shortcut.

Method 1: iteration (repeated substitution)

Expand the recurrence again and again until a pattern appears, write the k-th step in general, then choose k so that you hit the base case.

Example A: T(n) = T(n/2) + 1, T(1) = 1

T(n) = T(n/2) + 1 = [T(n/4) + 1] + 1 = T(n/4) + 2 = [T(n/8) + 1] + 2 = T(n/8) + 3 … = T(n/2ᵏ) + k ← general step k Put n/2ᵏ = 1, i.e. k = log₂n: T(n) = T(1) + log₂n = 1 + log₂n = Θ(log n)

Example B: T(n) = 2T(n−1) + 1, T(1) = 1 (Towers of Hanoi)

T(n) = 2T(n−1) + 1 = 2[2T(n−2) + 1] + 1 = 4T(n−2) + 2 + 1 = 4[2T(n−3) + 1] + 2 + 1 = 8T(n−3) + 4 + 2 + 1 … = 2ᵏ T(n−k) + (2ᵏ⁻¹ + … + 2 + 1) = 2ᵏ T(n−k) + 2ᵏ − 1 Put n − k = 1, i.e. k = n − 1: T(n) = 2ⁿ⁻¹·1 + 2ⁿ⁻¹ − 1 = 2ⁿ − 1 = Θ(2ⁿ)
The pattern in iteration

Write at least three expansions so the general k-th term is obvious, check it against the first line, then solve "argument of T = base case" for k.

Method 2: substitution (guess and prove)

Guess the answer (from iteration, a recursion tree or experience), then prove it by mathematical induction, finding constants that make the inequality work.

Example C: show T(n) = 4T(n/2) + n is O(n²)

First attempt fails

Assume T(m) ≤ c·m² for all m < n. Then T(n) ≤ 4c(n/2)² + n = cn² + n. We needed ≤ cn², but we got cn² plus n. The induction does not close, even though the guess is right.

Fix: subtract a lower-order term

Assume the stronger claim T(m) ≤ c·m² − d·m. Then

T(n) ≤ 4[c(n/2)² − d(n/2)] + n = cn² − 2dn + n = cn² − dn − (dn − n)

This is ≤ cn² − dn whenever dn − n ≥ 0, i.e. d ≥ 1. Choose c large enough for the base case. So T(n) = O(n²).

The classic wrong proof

Writing "T(n) ≤ cn² + n = O(n²), done" is invalid. In an induction you must prove the exact form you assumed (≤ cn²) with the same constant c. "+ n" breaks it.

Changing variables

Recurrences with square roots become familiar after substituting m = log n.

T(n) = 2T(√n) + 1. Let n = 2ᵐ, so √n = 2^(m/2). T(2ᵐ) = 2T(2^(m/2)) + 1. Define S(m) = T(2ᵐ): S(m) = 2S(m/2) + 1 → Θ(m) (Master theorem, case 1) T(n) = S(log n) = Θ(log n)

Recursion trees and the Master theorem

Draw every recursive call as a node holding the work it does outside its children. Add the work level by level. That picture also explains the Master theorem.

Recursion tree for T(n) = 2T(n/2) + n

Each level holds total work n, and there are log₂n + 1 levels (from n down to size 1). Total = n log₂n + n = Θ(n log n). The steps are always the same:

  1. Draw the root with cost f(n), its a children with cost f(n/b), and so on.
  2. Find the cost of level i: (number of nodes) × (cost per node) = aⁱ · f(n/bⁱ).
  3. Find the height: the subproblem size n/bⁱ reaches 1 when i = logbn.
  4. Count the leaves: a^(logbn) = n^(logba), each costing T(1).
  5. Add all levels (often a geometric series) plus the leaves.

Example: T(n) = 3T(n/4) + n²

Level 0: 1 node × n² = n² Level 1: 3 nodes × (n/4)² = (3/16) n² Level 2: 9 nodes × (n/16)² = (3/16)² n² Level i: 3ⁱ nodes × (n/4ⁱ)² = (3/16)ⁱ n² Height = log₄n, leaves = 3^(log₄n) = n^(log₄3) ≈ n^0.79 Sum ≤ n² · (1 + 3/16 + (3/16)² + …) = n² · 1/(1 − 3/16) = (16/13) n² T(n) = Θ(n²) ← the root dominates; costs shrink level by level

Unequal splits: T(n) = T(n/4) + T(3n/4) + n

Every full level still sums to n (n/4 + 3n/4 = n). The leftmost path shrinks fastest and ends after log₄n levels; the rightmost path (always taking 3n/4) is the longest, with log4/3n levels. Below the shortest path some levels are incomplete and sum to less than n. So

n · log₄n ≤ T(n) ≤ n · log4/3n  ⇒  T(n) = Θ(n log n)

Master theorem

For recurrences of the form T(n) = a·T(n/b) + f(n) with constants a ≥ 1, b > 1, compare f(n) against n^(log_b a), which is the number of leaves (the total cost of the bottom level).

When the Master theorem does not apply

• a < 1 or b ≤ 1, or a, b not constants (e.g. T(n) = nT(n/2) + n).

• Subtract-type recurrences like T(n) = T(n−1) + n. Use iteration.

• f(n) is bigger or smaller than n^(log_b a) but not by a polynomial factor nᵉ, e.g. 2T(n/2) + n/log n, which falls in the gap between cases 1 and 2.

• Case 3 with regularity failing (rare, e.g. f(n) with oscillating sin terms).

• f(n) negative or not asymptotically positive.

AVL trees

A binary search tree is fast only while it stays bushy. An AVL tree checks its balance after every insertion and deletion and repairs it with rotations, so the height stays O(log n).

Balance factor

For every node: BF = height(left subtree) − height(right subtree), where an empty subtree has height 0 (some books use −1; the differences are what matter). An AVL tree requires BF ∈ {−1, 0, +1} at every node. A node with BF = +2 is too heavy on the left; −2 is too heavy on the right.

Why the height is O(log n)

The thinnest AVL tree of height h has N(h) = N(h−1) + N(h−2) + 1 nodes, a Fibonacci-like growth, so N(h) grows like 1.618ʰ. That means h ≤ about 1.44 log₂n. Search, insert and delete are all O(log n).

The four rotations

After inserting a key, walk up from the new node. The first node with |BF| = 2 is the pivot z. Look at the first two steps from z down toward the new node. Those two steps name the case.

In LR and RL, the grandchild x ends up as the new root of that subtree, with z and y as its two children. The three keys sort as y < x < z (LR) or z < x < y (RL); the middle key goes on top. x's old subtrees are split between y and z.

Deletion

  1. Delete as in a normal BST. A leaf is removed directly. A node with one child is replaced by that child. A node with two children takes the key of its in-order successor (smallest key in the right subtree, or use the predecessor if your teacher does), and then that successor node is deleted instead.
  2. Walk up from the parent of the node that was physically removed, updating heights.
  3. At every node with |BF| = 2, rotate. Unlike insertion, deletion may need rotations at several ancestors, all the way up to the root.

Disjoint sets (union–find)

Keep track of items split into groups that never overlap, and answer "are these two in the same group?" quickly while groups keep merging. Kruskal's algorithm and connected components both depend on it.

The three operations

Each set is identified by one of its members, called the representative.

MAKE-SET(x)

Create a new set {x}. x is its own representative.

FIND-SET(x)

Return the representative of x's set. Two items are in the same set exactly when FIND-SET gives the same answer for both.

UNION(x, y)

Merge the set containing x with the set containing y into one set.

When we analyse these, n is the number of MAKE-SET operations (the number of items) and m is the total number of operations of all three kinds. At most n − 1 unions are possible, because each one reduces the number of sets by one.

Representation 1: linked lists

Each set is a linked list. The set object has a head (the representative) and a tail. Every member stores a pointer back to the set object.

  • FIND-SET(x): follow x's back pointer to the head. O(1).
  • UNION(x, y): append y's list after x's tail, then update the back pointer of every element that moved. Cost = size of the appended list.
Why plain linked-list union is slow

Start with n singletons and always append the bigger list onto the single new item: UNION(x2, x1), UNION(x3, x2), … The i-th union moves i elements, for a total of 1 + 2 + … + (n−1) = Θ(n²).

Weighted-union heuristic

Store each list's length and always append the shorter list onto the longer one. Then a sequence of m operations, n of them MAKE-SET, takes O(m + n log n).

Why: follow one element x. Its back pointer is updated only when x is in the smaller list. After that union, x's set is at least twice as big as before. A set can double at most log₂n times before it holds all n elements, so x's pointer changes at most log₂n times. Over n elements that is O(n log n) for all unions, plus O(1) for each of the m operations.

Representation 2: a forest of trees

Each set is a tree. Every node points to its parent; the root points to itself and is the representative. FIND-SET walks up to the root; UNION makes one root the child of the other.

Array representation

Since each node stores just one parent, the whole forest fits in an array p[1..n]. Roots are marked with p[i] = i (CLRS) or p[i] = −1 (Horowitz; weighted versions store −size at the root).

Two heuristics that make it fast

Union by rank

Each root keeps a rank, an upper bound on its tree's height. Link the root with smaller rank under the larger. Only when ranks are equal does the new root's rank go up by 1. Tree height stays ≤ log₂n.

Path compression

During FIND-SET(x), make every node on the path from x to the root point directly to the root. The next find on any of them takes one step. Ranks are not changed by compression.

MAKE-SET(x):   x.p = x;  x.rank = 0

FIND-SET(x):
    if x ≠ x.p:
        x.p = FIND-SET(x.p)      // path compression
    return x.p

UNION(x, y):  LINK(FIND-SET(x), FIND-SET(y))

LINK(a, b):                    // a, b are roots
    if a.rank > b.rank:  b.p = a
    else:                a.p = b
        if a.rank == b.rank:  b.rank = b.rank + 1

On a tie, CLRS's LINK puts the first root under the second. Many question papers state the opposite rule ("make the second root a child of the first"). Read the rule given in the question; the stepper below lets you choose either.

Connected components with disjoint sets

A connected component of an undirected graph is a largest group of vertices that can all reach each other. Feeding the edges to union–find builds the components one edge at a time.

The algorithm

CONNECTED-COMPONENTS(G):
    for each vertex v in G.V:
        MAKE-SET(v)
    for each edge (u, v) in G.E:
        if FIND-SET(u) ≠ FIND-SET(v):
            UNION(u, v)

SAME-COMPONENT(u, v):
    return FIND-SET(u) == FIND-SET(v)

Start with every vertex alone. Each edge says "these two are connected", so their sets merge. An edge whose ends are already in one set adds nothing new (it would close a cycle). After all edges, each set is exactly one connected component.

Cost

V MAKE-SETs, 2E FIND-SETs and at most V − 1 UNIONs, so O((V + E)·α(V)) with both heuristics, practically linear. This is better than BFS/DFS when edges arrive one at a time (the graph keeps growing), because union–find never has to start over.

Breadth-first search (BFS)

BFS explores in rings: first the start vertex s, then all vertices one edge away, then two edges away, and so on. A queue (first in, first out) produces this order.

BFS(G, s):
    for each u: color[u] = WHITE, d[u] = ∞, π[u] = NIL
    color[s] = GRAY; d[s] = 0; Q = ⟨s⟩
    while Q not empty:
        u = DEQUEUE(Q)
        for each v in Adj[u]:
            if color[v] == WHITE:          // first time we see v
                color[v] = GRAY; d[v] = d[u] + 1; π[v] = u
                ENQUEUE(Q, v)
        color[u] = BLACK
  • White = not yet seen, gray = seen and waiting in the queue, black = finished.
  • d[v] is the shortest-path distance in number of edges from s. BFS solves shortest paths in unweighted graphs.
  • The edges (π[v], v) form the BFS tree.
  • Time: each vertex is enqueued once, each adjacency list is scanned once: O(V + E) with lists, O(V²) with a matrix.

Depth-first search (DFS)

DFS goes as deep as it can along one path, and only backs up when it hits a dead end. It uses recursion (or an explicit stack). Each vertex gets two timestamps: d[u] when it is discovered and f[u] when all its descendants are done.

DFS(G):
    for each u: color[u] = WHITE
    time = 0
    for each u in G.V:
        if color[u] == WHITE: DFS-VISIT(u)

DFS-VISIT(u):
    time = time + 1; d[u] = time; color[u] = GRAY
    for each v in Adj[u]:
        if color[v] == WHITE: π[v] = u; DFS-VISIT(v)
    color[u] = BLACK; time = time + 1; f[u] = time

For any two vertices, the intervals [d, f] are either nested (one is a descendant of the other) or disjoint, never partly overlapping, like matched brackets. A directed graph has a cycle if and only if DFS finds a back edge, i.e. it reaches a gray vertex.

Topological sorting

Given tasks with "must happen before" rules, list them in an order that obeys every rule. In graph terms: order the vertices of a directed graph so every edge points forward.

What it is, and when it exists

A topological order of a directed graph is a linear ordering of its vertices such that for every edge u → v, u comes before v. Think of getting dressed: socks before shoes, shirt before tie.

A topological order exists if and only if the graph is a DAG (directed acyclic graph)

Cycle ⇒ no order: on a cycle v₁ → v₂ → … → vₖ → v₁, each vertex must come before the next, so v₁ must come before itself. Impossible.

DAG ⇒ order exists: a DAG always has a vertex with in-degree 0 (otherwise walk backwards along incoming edges forever; with finitely many vertices you would repeat one, which is a cycle). Put that vertex first, delete it, and the rest is still a DAG. Repeat.

A DAG can have many valid orders. Any one of them is a correct answer.

Method 1: DFS finishing times

TOPOLOGICAL-SORT(G):
    run DFS(G) to compute finishing times f[v]
    as each vertex finishes, insert it at the FRONT of a linked list
    return the list           // = vertices in decreasing f[v]

Why it works: in a DAG, for every edge u → v we get f[v] < f[u]. When DFS explores u → v, v cannot be gray (that would be a back edge, i.e. a cycle). If v is white it becomes u's descendant and finishes first; if v is black it already finished. Either way u finishes later, so u lands in front. Time O(V + E).

Method 2: source removal (Kahn's algorithm)

KAHN(G):
    compute in-degree of every vertex
    Q = all vertices with in-degree 0
    while Q not empty:
        u = remove from Q;  append u to the output
        for each v in Adj[u]:
            indeg[v] = indeg[v] − 1
            if indeg[v] == 0: add v to Q
    if output has fewer than V vertices: the graph has a cycle

Computing in-degrees is O(V + E), every vertex enters Q once, and every edge is decremented once: O(V + E). A bonus: if some vertices never reach in-degree 0, they are on or behind a cycle, so Kahn's method also detects cycles.

Strongly connected components

In a directed graph, a strongly connected component (SCC) is a largest group of vertices where every vertex can reach every other one. Kosaraju's algorithm finds all of them with two depth-first searches.

The idea

Two vertices u and v are in the same SCC if there is a path u ⇝ v and a path v ⇝ u. Shrink every SCC to a single vertex and you get the component graph GSCC.

The component graph is always a DAG

Suppose there were a cycle between two components C and C′. Then every vertex of C could reach every vertex of C′ and back, so C and C′ would be one bigger SCC. That contradicts C and C′ being maximal.

Kosaraju's algorithm (two DFS passes)

STRONGLY-CONNECTED-COMPONENTS(G):
1   call DFS(G) to compute finishing times f[u]
2   compute Gᵀ  (reverse every edge)
3   call DFS(Gᵀ), but in the main loop take vertices
    in order of decreasing f[u] from step 1
4   each DFS tree formed in step 3 is one SCC

Why it works, intuitively: the vertex that finishes last in pass 1 sits in a "source" component of the component DAG, one with no incoming edges from other components. Reversing all edges turns that component into a sink: from inside it, the second DFS cannot leak into any other component, so its tree is exactly that SCC. Then the next-highest unvisited vertex starts the next SCC, and so on.

Time: two DFS runs plus building Gᵀ, all O(V + E) with adjacency lists. Gᵀ and G have exactly the same SCCs, since reversing edges keeps "u and v reach each other".

Divide and conquer, and merge sort

Split the problem into smaller copies of itself, solve those recursively, then combine their answers. Merge sort is the cleanest example.

Control abstraction

A control abstraction is the skeleton every algorithm of a design strategy follows, with the problem-specific parts left as named functions.

Algorithm DAndC(P)
{
    if Small(P) then return S(P);          // solve tiny instances directly
    else
    {
        divide P into smaller instances P₁, P₂, …, Pₖ,  k ≥ 1;
        apply DAndC to each of these subproblems;
        return Combine(DAndC(P₁), DAndC(P₂), …, DAndC(Pₖ));
    }
}

Its running time follows the same shape:

T(n) = g(n) if n is small T(n) = T(n₁) + T(n₂) + … + T(nₖ) + f(n) otherwise

g(n) is the cost of solving a small instance directly, and f(n) is the cost of dividing and combining. With k equal parts of size n/b this becomes the Master-theorem form a·T(n/b) + f(n).

Merge sort

  • Divide: split the array into two halves at mid = ⌊(low + high)/2⌋.
  • Conquer: sort each half recursively. A one-element array is already sorted (Small(P)).
  • Combine: merge the two sorted halves into one sorted array.
MERGE-SORT(A, low, high):
    if low < high:
        mid = ⌊(low + high) / 2⌋
        MERGE-SORT(A, low, mid)
        MERGE-SORT(A, mid + 1, high)
        MERGE(A, low, mid, high)

MERGE(A, low, mid, high):
    i = low; j = mid + 1; k = low           // B is a temporary array
    while i ≤ mid and j ≤ high:
        if A[i] ≤ A[j]: B[k] = A[i]; i++
        else:           B[k] = A[j]; j++
        k++
    copy any leftover A[i..mid] or A[j..high] into B
    copy B[low..high] back into A[low..high]
How many comparisons does MERGE make?

Each comparison sends exactly one element to the output. Once one list runs out, the rest of the other list is copied with no comparisons. Merging lists of sizes m and n therefore needs at most m + n − 1 comparisons, and as few as min(m, n) when every element of the shorter list is smaller than everything in the longer one.

Strassen's matrix multiplication

The schoolbook method multiplies two n×n matrices with n³ scalar multiplications. Strassen found a way to multiply 2×2 blocks with 7 multiplications instead of 8, and applying that recursively beats n³.

Plain divide and conquer gains nothing

Split each n×n matrix into four n/2 × n/2 blocks:

[ C11 C12 ] [ A11 A12 ] [ B11 B12 ] [ C21 C22 ] = [ A21 A22 ] [ B21 B22 ] C11 = A11·B11 + A12·B21 C12 = A11·B12 + A12·B22 C21 = A21·B11 + A22·B21 C22 = A21·B12 + A22·B22

That is 8 block multiplications and 4 block additions (each addition costs (n/2)² = Θ(n²)):

T(n) = 8T(n/2) + Θ(n²) → n^(log₂8) = n³ dominates → Θ(n³)

Same as the ordinary triple loop. The recursion only pays off if we cut down the number of multiplications, since that number (a) sits in the exponent log₂a.

The greedy method and fractional knapsack

A greedy algorithm builds its answer one piece at a time, always taking whatever looks best right now and never undoing a choice. It is fast and simple, but it only gives the optimum for problems with the right structure.

Words you need

  • Objective function: the quantity to maximise or minimise (total profit, total cost).
  • Feasible solution: any answer that satisfies the constraints (fits in the knapsack, forms a tree…).
  • Optimal solution: a feasible solution with the best objective value.

Control abstraction

Algorithm Greedy(a, n)       // a[1..n] holds the n inputs
{
    solution := ∅;
    for i := 1 to n do
    {
        x := Select(a);                     // pick the best remaining input
        if Feasible(solution ∪ {x}) then
            solution := Union(solution, x);
    }
    return solution;
}

Select chooses by a greedy criterion and removes the input from a. Feasible checks that adding it keeps the solution valid. Union adds it. Every greedy algorithm in this module (knapsack, Kruskal, Prim, Dijkstra) fills in these three functions differently.

Fractional knapsack

You have a knapsack of capacity M and n objects. Object i has weight wᵢ and profit pᵢ. You may take any fraction xᵢ of an object (think gold dust, not gold bars) and earn pᵢxᵢ.

maximise Σ pᵢ xᵢ subject to Σ wᵢ xᵢ ≤ M, 0 ≤ xᵢ ≤ 1, 1 ≤ i ≤ n

Greedy criterion: take objects in decreasing order of profit per unit weight pᵢ/wᵢ. Take each one whole while it fits; take a fraction of the first one that does not fit; stop.

Algorithm GreedyKnapsack(M, n)
// p[1..n], w[1..n] already sorted so that p[i]/w[i] ≥ p[i+1]/w[i+1]
{
    for i := 1 to n do x[i] := 0.0;
    U := M;                                     // remaining capacity
    for i := 1 to n do
    {
        if (w[i] > U) then break;
        x[i] := 1.0;  U := U − w[i];
    }
    if (i ≤ n) then x[i] := U / w[i];
}

Time: sorting by ratio is O(n log n) and the loop is O(n), so O(n log n) overall (O(n) if the input is already sorted).

Worked example

n = 5, M = 16, profits (24, 30, 18, 10, 14), weights (6, 15, 3, 10, 4).

Order by ratio: 3, 1, 5, 2, 4. Take object 3 (weight 3, profit 18, room left 13), object 1 (6, 24, room 7), object 5 (4, 14, room 3). Object 2 weighs 15, so take 3/15 = 0.2 of it for profit 6. Room left 0.

x = (1, 0.2, 1, 0, 1), total profit = 18 + 24 + 14 + 6 = 62. Compare other greedy rules: largest profit first gives 34; smallest weight first gives 59. Only the ratio rule is always optimal.

Why the ratio rule is optimal (exchange argument)

Take any optimal solution that differs from the greedy one. Somewhere it uses less of a high-ratio object i and more of a lower-ratio object j. Swap a small weight δ of j for the same weight of i: the total weight is unchanged and the profit changes by δ(pᵢ/wᵢ − pⱼ/wⱼ) ≥ 0. Repeating such swaps turns the optimal solution into the greedy one without ever losing profit, so greedy is optimal too.

Minimum cost spanning trees: Kruskal and Prim

Connect every town with roads using the least total road length. That is a minimum spanning tree (MST), and two greedy algorithms find one.

Definitions

For a connected, undirected, weighted graph G = (V, E), a spanning tree is a subset of edges that connects all vertices with no cycle. It always has exactly V − 1 edges. A minimum spanning tree has the smallest total weight among all spanning trees. If all weights are distinct, the MST is unique.

Why greedy works here: the cut property

Split the vertices into any two groups. The lightest edge crossing between the groups is safe: it belongs to some MST. Both algorithms keep adding such a "lightest crossing edge"; they differ only in which cut they look at.

Kruskal's algorithm

Look at edges from lightest to heaviest. Accept an edge if it joins two different trees; reject it if both ends are already in the same tree (it would make a cycle). Disjoint sets answer "same tree?" quickly.

MST-KRUSKAL(G, w):
    A = ∅
    for each vertex v: MAKE-SET(v)
    sort the edges of E into non-decreasing order of weight
    for each edge (u, v) in that order:
        if FIND-SET(u) ≠ FIND-SET(v):
            A = A ∪ {(u, v)}
            UNION(u, v)
    return A

Time: sorting O(E log E). Then 2E finds and V − 1 unions cost O(E α(V)). Since E ≤ V², log E ≤ 2 log V, so the total is O(E log E) = O(E log V). Sorting dominates.

Prim's algorithm

Grow one tree from a start vertex r. At each step add the cheapest edge from the tree to a vertex not yet in it. Each outside vertex v keeps key[v] = the weight of its cheapest edge into the tree so far.

MST-PRIM(G, w, r):
    for each u: key[u] = ∞; π[u] = NIL
    key[r] = 0
    Q = min-priority queue of all vertices, keyed by key[]
    while Q not empty:
        u = EXTRACT-MIN(Q)                // u joins the tree via edge (π[u], u)
        for each v in Adj[u]:
            if v ∈ Q and w(u, v) < key[v]:
                π[v] = u; key[v] = w(u, v)   // DECREASE-KEY

Time with a binary min-heap: V EXTRACT-MINs at O(log V) each, and up to E DECREASE-KEYs at O(log V) each: O((V + E) log V) = O(E log V). With a plain array instead of a heap (scan for the minimum): O(V²). With a Fibonacci heap: O(E + V log V).

Dijkstra's single-source shortest paths

Find the cheapest route from one source vertex to every other vertex, when no edge has a negative weight. It looks like Prim's algorithm, but the key of a vertex is its total distance from the source instead of one edge weight.

Relaxation

Every vertex v keeps an estimate d[v] of its distance from the source s (start: d[s] = 0, all others ∞) and a predecessor π[v]. Relaxing edge (u, v) asks: "is going through u a shortcut to v?"

RELAX(u, v, w):
    if d[u] + w(u, v) < d[v]:
        d[v] = d[u] + w(u, v)
        π[v] = u

The algorithm

DIJKSTRA(G, w, s):
    for each v: d[v] = ∞; π[v] = NIL
    d[s] = 0
    S = ∅                               // vertices whose distance is final
    Q = min-priority queue of all vertices, keyed by d[]
    while Q not empty:
        u = EXTRACT-MIN(Q)              // greedy choice
        S = S ∪ {u}
        for each v in Adj[u]:
            RELAX(u, v, w)              // DECREASE-KEY if d[v] drops
Why the greedy choice is safe

When u has the smallest d among unfinished vertices, any other route to u would have to leave the finished set S through some unfinished vertex y with d[y] ≥ d[u], and then continue along edges of weight ≥ 0. Such a route can never come back cheaper than d[u]. So d[u] is final the moment u is extracted. This argument breaks as soon as an edge can be negative.

Dynamic programming

When a recursive solution keeps solving the same subproblems again and again, solve each one once and store the answer in a table. That is dynamic programming (DP).

When DP applies

Optimal substructure

An optimal solution is built from optimal solutions to its subproblems.

Overlapping subproblems

The same smaller problems come up again and again. (In divide and conquer, like merge sort, they do not.)

Seeing the overlap: binomial coefficients

C(n, k) = C(n−1, k−1) + C(n−1, k), with C(n, 0) = C(n, n) = 1. Plain recursion recomputes the same values many times:

The plain recursion makes 2·C(n, k) − 1 calls, which is exponential: for C(30, 15) that is over 300 million calls, yet there are only 30 × 15 different subproblems. DP fills Pascal's triangle row by row instead, each entry once: O(nk) time.

Control abstraction (the four steps)

  1. Characterise the structure of an optimal solution: what are the subproblems?
  2. Recursively define the value of an optimal solution in terms of smaller subproblems (the recurrence).
  3. Compute the values bottom-up, smallest subproblems first, storing them in a table.
  4. Construct an optimal solution from the stored information (keep a second table of the choices made).

Step 3 can also be done top-down with memoisation: write the plain recursion, but check a table before computing and store each result after. Same complexity, easier to write.

Principle of optimality

Bellman's principle of optimality

An optimal sequence of decisions has the property that, whatever the initial state and first decision are, the remaining decisions must form an optimal sequence with respect to the state that results from the first decision.

In plain words: every piece of an optimal solution is itself optimal for its own subproblem. DP is only correct when this holds.

Holds: shortest paths

If the shortest route P → R → T passes through R, then its P → R part must be a shortest P → R route. If a shorter P → R route existed, swapping it in would make the whole route shorter: a contradiction ("cut and paste").

Fails: longest simple paths

Triangle with vertices a, b, c, all edges weight 1. The longest simple path from a to c is a → b → c (length 2). Its piece a → b has length 1, but the longest simple path from a to b is a → c → b (length 2). The subpaths are not optimal, because the two halves compete for the same vertices.

Matrix chain multiplication

Multiplying matrices is associative, so (AB)C = A(BC), but the two orders can cost wildly different amounts of work. DP finds the cheapest bracketing.

The problem

Multiplying a p×q matrix by a q×r matrix takes p·q·r scalar multiplications. A chain A₁A₂…Aₙ where Aᵢ has dimensions pi−1 × pᵢ is described by the list ⟨p₀, p₁, …, pₙ⟩.

Why the order matters

A (10×100), B (100×5), C (5×50). (AB)C costs 10·100·5 + 10·5·50 = 5,000 + 2,500 = 7,500. A(BC) costs 100·5·50 + 10·100·50 = 25,000 + 50,000 = 75,000. Ten times more work for the same answer.

Trying every bracketing is hopeless: the number of bracketings is the Catalan number, which grows like 4ⁿ/n^1.5.

DP formulation

Let m[i, j] = the minimum cost of computing Aᵢ…Aⱼ. The last multiplication splits the chain at some k: (Aᵢ…Aₖ)(Aₖ₊₁…Aⱼ). The left part is pi−1×pₖ and the right part is pₖ×pⱼ, so the final multiplication costs pi−1·pₖ·pⱼ.

Recurrence
m[i, i] = 0 m[i, j] = min over i ≤ k < j of { m[i, k] + m[k+1, j] + pi−1·pₖ·pⱼ } s[i, j] = the k that gave the minimum

Fill the table by chain length: first all chains of length 2 (the diagonal just above the main one), then length 3, and so on up to m[1, n]. Each entry only needs shorter chains, which are already done.

MATRIX-CHAIN-ORDER(p):           // p = ⟨p0, …, pn⟩
    for i = 1 to n: m[i, i] = 0
    for L = 2 to n:                    // chain length
        for i = 1 to n − L + 1:
            j = i + L − 1;  m[i, j] = ∞
            for k = i to j − 1:
                q = m[i, k] + m[k+1, j] + p[i−1]·p[k]·p[j]
                if q < m[i, j]: m[i, j] = q; s[i, j] = k

Floyd–Warshall: all-pairs shortest paths

Distances between every pair of vertices at once, by allowing more and more vertices to be used as stopovers. It is a dynamic program that works even with negative edges.

The idea

Number the vertices 1…n. Let Dᵏ[i][j] be the shortest distance from i to j using only vertices from {1, …, k} as intermediate stops. D⁰ is just the edge-weight matrix (0 on the diagonal, ∞ where there is no edge). At step k, the best i → j route either avoids k (the old value) or goes i → k → j:

Recurrence
Dᵏ[i][j] = min( Dᵏ⁻¹[i][j], Dᵏ⁻¹[i][k] + Dᵏ⁻¹[k][j] )
FLOYD-WARSHALL(W):              // W = n×n weight matrix
    D = W
    for k = 1 to n:
        for i = 1 to n:
            for j = 1 to n:
                if D[i][k] + D[k][j] < D[i][j]:
                    D[i][j] = D[i][k] + D[k][j]
                    P[i][j] = P[k][j]        // predecessor, to rebuild paths
    return D

Analysis: three nested loops: Θ(n³) time, Θ(n²) space (one matrix can be updated in place, because row k and column k do not change during step k).

Doing it by hand quickly

In Dᵏ, row k and column k are copied unchanged, and so is the diagonal. For every other cell, compare the old value with (row-k entry in its column) + (column-k entry in its row). If row k or column k has ∞ in that position, the cell cannot change.

Negative edges and negative cycles

Negative edge weights are fine. A negative-weight cycle is not: going around it again and again makes the path cheaper without limit, so "shortest path" has no meaning for vertices that can reach the cycle. Floyd–Warshall then gives meaningless numbers, but it does reveal the problem: some vertex ends with D[i][i] < 0 (a route from i back to itself with negative total). Check the diagonal of the final matrix.

Backtracking and the N-Queens problem

Build a solution one component at a time. The moment a partial solution cannot possibly be completed, abandon it and go back to try the next option. This prunes huge parts of the search.

Vocabulary

  • The solution is a tuple (x₁, x₂, …, xₙ), chosen one component at a time.
  • Explicit constraints restrict each xᵢ to a set of values on its own. N-Queens: xᵢ ∈ {1, …, n}, the column of the queen in row i.
  • Implicit constraints relate components to each other. N-Queens: no two queens share a column (xᵢ ≠ xⱼ) or a diagonal (|xᵢ − xⱼ| ≠ |i − j|).
  • The state space tree has one level per component; each path from the root is a partial tuple.
  • A bounding function tests a node: if the partial tuple already breaks a constraint, the node is killed and its whole subtree is skipped.
  • Node states: live (generated, children not all generated), E-node (being expanded now), dead (fully explored or killed).

Control abstraction

Algorithm Backtrack(k)
// x[1..k−1] has been chosen; try every value for x[k]
{
    for (each x[k] ∈ T(x[1], …, x[k−1])) do
    {
        if (B_k(x[1], x[2], …, x[k]) ≠ false) then    // bounding function
        {
            if (x[1], …, x[k]) is a path to an answer node
                then write (x[1:k]);
            if (k < n) then Backtrack(k + 1);
        }
    }
}

T(…) gives the candidate values for the next component; Bk is the bounding function. Backtracking is a depth-first search of the state space tree that skips killed subtrees.

N-Queens

Place n queens on an n×n board so that no two attack each other (same row, column or diagonal). One queen per row is automatic, so x[k] is the column of the queen in row k.

Algorithm Place(k, i)
// true if a queen can go in row k, column i
{
    for j := 1 to k − 1 do
        if ((x[j] = i)                          // same column
            or (Abs(x[j] − i) = Abs(j − k)))     // same diagonal
        then return false;
    return true;
}

Algorithm NQueens(k, n)
{
    for i := 1 to n do
    {
        if Place(k, i) then
        {
            x[k] := i;
            if (k = n) then write (x[1:n]);
            else NQueens(k + 1, n);
        }
    }
}

Call NQueens(1, n). Place is O(k), and the worst case explores an exponential number of nodes, but bounding kills most of them early. Solutions: 4 queens has 2, 5 has 10, 8 has 92.

LC search and the cost function

Every node X gets an estimate ĉ(X) of the cost of the best answer in its subtree. For minimisation, ĉ is a lower bound: no solution below X can cost less than ĉ(X). Least-cost (LC) search always picks the live node with the smallest ĉ as the next E-node.

Control abstraction (LC search)

Algorithm LCSearch(t)          // t = root of the state space tree
{
    if t is an answer node then { output t; return; }
    E := t;                              // E-node
    initialise the list of live nodes to be empty;
    repeat
    {
        for each child x of E do
        {
            if x is an answer node then { output path from x to t; return; }
            Add(x);                       // x becomes a live node
            (x → parent) := E;            // to rebuild the path
        }
        if there are no more live nodes then { write ("No answer node"); return; }
        E := Least();                     // remove the live node with smallest ĉ
    } until (false);
}

With a FIFO queue in place of Least() it becomes FIFO branch and bound; with a stack, LIFO branch and bound. For optimisation problems, a common refinement: stop when the node chosen by Least() is itself a complete solution, because every other live node has ĉ at least as large.

Find the cheapest tour that starts at city 1, visits every city exactly once and returns to 1. The cost matrix A has A[i][j] = cost of going from i to j, and ∞ on the diagonal.

Step 1: reduce the matrix to get a lower bound

Every tour leaves each city exactly once, so it must pay at least the cheapest entry of each row. Subtract each row's minimum from that row. Every tour also enters each city once, so then subtract each column's minimum from that column. Let r = the total subtracted. Every tour costs at least r, so r is a lower bound, and the root gets ĉ(root) = r. A matrix is reduced when every row and column has a 0 (or is all ∞).

Tractable and intractable problems: P, NP, NP-hard, NP-complete

Some problems have fast algorithms; for others, nobody has found one in fifty years of trying. Complexity classes sort problems by how hard they are, and reductions let us compare the hardness of two problems.

Tractable vs intractable

A problem is tractable if some algorithm solves it in polynomial time, O(nᵏ) for a constant k (sorting n log n, shortest paths, MST). It is intractable if no polynomial algorithm exists, or none is known, and the best algorithms are exponential (2ⁿ, n!). The line is drawn at polynomial because polynomials stay manageable as n grows and are closed under composition, while 2ⁿ doubles with every extra input item.

Decision vs optimisation problems

Optimisation problem

Asks for the best value. "What is the cheapest tour?" "What is the largest clique?"

Decision problem

Has a yes/no answer. "Is there a tour of cost ≤ k?" "Is there a clique of size ≥ k?"

Complexity classes are defined for decision problems. That loses nothing important: if the decision version is hard, the optimisation version is at least as hard (solving the optimisation answers the decision immediately). Conversely, a decision algorithm plus binary search on k usually finds the optimum.

The classes

P

Decision problems solvable in polynomial time by a deterministic algorithm. Examples: sorting, MST, shortest path, "is there a path from u to v?"

NP

Decision problems whose yes-answers can be verified in polynomial time, given a certificate (a proposed solution). Equivalently: solvable in polynomial time by a nondeterministic machine that "guesses" the certificate. NP means nondeterministic polynomial, not "not polynomial".

NP-hard

Problems at least as hard as every problem in NP: every NP problem reduces to it in polynomial time. An NP-hard problem need not be in NP, and need not even be a decision problem.

NP-complete

Problems that are both in NP and NP-hard: the hardest problems inside NP. Examples: SAT, 3-CNF-SAT, CLIQUE, VERTEX-COVER, decision TSP, Hamiltonian cycle, subset sum.

Certificates: how to show a problem is in NP

Describe the certificate and a polynomial-time check. Decision TSP ("tour of cost ≤ k?"): the certificate is the order of cities. Check it visits each city exactly once (O(n)), add up the n edge costs and compare with k (O(n)). That is polynomial, so decision TSP ∈ NP.

Every problem in P is also in NP (the verifier can just solve the problem itself and ignore the certificate), so P ⊆ NP. Whether P = NP is the most famous open question in computer science. Almost everyone believes P ≠ NP.

NP-hard but not NP-complete: the halting problem ("does program M stop on input x?") is NP-hard (SAT reduces to it: build a program that tries every assignment and halts if one satisfies the formula), but it is undecidable, so it is certainly not in NP. Optimisation TSP ("find the cheapest tour") is NP-hard but is not a decision problem, so it is not in NP either.

Polynomial-time reductions

A reduction from problem A to problem B, written A ≤ₚ B, is a polynomial-time function f that turns any instance x of A into an instance f(x) of B such that x is a yes-instance of A ⇔ f(x) is a yes-instance of B.

So if B is easy, A is easy too: transform, then solve B. Read the other way: if A is hard, B must be at least as hard. This is how hardness spreads from one problem to the next.

Recipe to prove a problem X is NP-complete

1. Show X ∈ NP: give a certificate and a polynomial-time verifier.

2. Pick a known NP-complete problem Y and show Y ≤ₚ X: build f, show it runs in polynomial time, and prove both directions of "x yes ⇔ f(x) yes".

Because ≤ₚ is transitive, every NP problem then reduces to X. The first NP-complete problem, SAT, was proved directly (Cook–Levin theorem).

If any NP-complete problem is in P, then P = NP

Let X be NP-complete with a polynomial algorithm. Take any problem L in NP. Since X is NP-hard, L ≤ₚ X: transform L's input in polynomial time, then run X's polynomial algorithm. A polynomial of a polynomial is still a polynomial, so L ∈ P. That holds for every L in NP, so NP ⊆ P, and with P ⊆ NP, P = NP.

Quick check

What does "NP" stand for?

Many NP problems (all of P, for instance) are solvable in polynomial time.

CLIQUE is NP-complete. Sorting and shortest path are in P; the halting problem is not in NP at all.

NP-completeness proofs: Clique and Vertex Cover

Two complete examples of the recipe: prove the problem is in NP, then reduce a known NP-complete problem to it.

Definitions

Clique

A clique in an undirected graph is a set of vertices that are all pairwise adjacent (a complete subgraph). CLIQUE = {⟨G, k⟩ : G has a clique of size k}.

Vertex cover

A vertex cover is a set of vertices that touches every edge: each edge has at least one endpoint in the set. VERTEX-COVER = {⟨G, k⟩ : G has a vertex cover of size k}.

3-CNF-SAT

A Boolean formula that is an AND of clauses, each clause an OR of exactly 3 literals (a variable or its negation). Is there an assignment making it true? Known NP-complete.

CLIQUE is NP-complete

Part 1: CLIQUE ∈ NP

Certificate: the set V′ of k vertices. Verifier: check |V′| = k, then check every pair u, v ∈ V′ is an edge. That is k(k−1)/2 ≤ |V|² edge checks, polynomial. So CLIQUE ∈ NP.

Part 2: 3-CNF-SAT ≤ₚ CLIQUE

Given a formula φ = C₁ ∧ C₂ ∧ … ∧ Cₖ with k clauses, build a graph G:

  1. For each clause Cr = (l₁ ∨ l₂ ∨ l₃), create 3 vertices, one per literal.
  2. Connect two vertices by an edge if (a) they come from different clauses, and (b) their literals are not complements of each other (not x and ¬x).
  3. Ask for a clique of size k (the number of clauses).

G has 3k vertices and at most 9k² edges, so it is built in polynomial time.

Proof of correctness (both directions)

(⇒) φ satisfiable ⇒ G has a k-clique. Take a satisfying assignment. Each clause has at least one true literal; pick one vertex for such a literal from every clause: k vertices. Any two of them are from different clauses, and both literals are true, so they cannot be x and ¬x. Hence every pair is joined by an edge: a k-clique.

(⇐) G has a k-clique ⇒ φ satisfiable. Vertices of the same clause are never adjacent, so a k-clique has exactly one vertex per clause. No two of its literals are complementary (they are all adjacent), so we can set every one of them true without conflict. Variables not mentioned can be anything. Each clause then has a true literal, so φ is satisfied.

VERTEX-COVER is NP-complete

The key fact: cliques and covers are complements

The complement graph Ḡ has the same vertices as G, and an edge exactly where G does not have one.

G has a clique of size k ⇔ Ḡ has a vertex cover of size |V| − k

(⇒) Let V′ be a clique in G. Take any edge (u, v) of Ḡ. Then (u, v) is not an edge of G, so u and v are not both in V′ (all pairs inside V′ are G-edges). So at least one of u, v is in V − V′: the set V − V′ covers every edge of Ḡ, and its size is |V| − k.

(⇐) Let V − V′ be a vertex cover of Ḡ. Take any u, v both in V′. If (u, v) were an edge of Ḡ, the cover V − V′ would have to contain u or v, but neither is in it. So (u, v) is not in Ḡ, i.e. it is an edge of G. Every pair in V′ is adjacent in G: V′ is a clique of size k.

The proof

  1. VERTEX-COVER ∈ NP. Certificate: the set V′ of k vertices. Check |V′| = k, then for every edge (u, v) check u ∈ V′ or v ∈ V′: O(V + E). Polynomial.
  2. CLIQUE ≤ₚ VERTEX-COVER. Given ⟨G, k⟩, output ⟨Ḡ, |V| − k⟩. Building Ḡ takes O(V²). By the fact above, G has a k-clique exactly when Ḡ has a vertex cover of size |V| − k.

CLIQUE is NP-complete, so VERTEX-COVER is NP-hard, and being in NP it is NP-complete.

Approximation algorithms: bin packing

For NP-hard optimisation problems we often give up on the exact optimum and accept a fast algorithm with a proven guarantee: "never more than twice the optimum", for example.

Approximation ratio

An algorithm has approximation ratio ρ(n) if, for every input of size n, its answer C and the optimum C* satisfy

max( C / C*, C* / C ) ≤ ρ(n)

For minimisation that means C ≤ ρ·C*; for maximisation, C ≥ C*/ρ. A ρ-approximation algorithm always runs in polynomial time. ρ = 1 would mean exact.

The bin packing problem

Given n items with sizes s₁, …, sₙ, each 0 < sᵢ ≤ 1, pack them into the fewest bins of capacity 1. It is NP-hard. One easy lower bound: the items' total size must fit, so OPT ≥ ⌈Σ sᵢ⌉.

Next Fit (NF)

Keep only the current bin open. If the item fits, put it in; otherwise close the bin forever and open a new one. O(n).

First Fit (FF)

Put the item into the first (lowest-numbered) bin with enough room; open a new bin only if none has room. O(n²) simply, O(n log n) with a tree.

Best Fit (BF)

Put the item into the bin where it fits most tightly (least room left afterwards). Ties go to the lowest-numbered bin.

First Fit Decreasing (FFD)

Sort items largest first, then run First Fit. Best Fit Decreasing (BFD) is the same idea with Best Fit. Sorting puts big awkward items in early, leaving small ones to fill the gaps.

AlgorithmGuarantee

Why Next Fit never uses more than 2·OPT bins

Look at any two consecutive bins Bᵢ and Bᵢ₊₁ in NF's packing. NF opened Bᵢ₊₁ because the next item did not fit in Bᵢ, so (contents of Bᵢ) + (contents of Bᵢ₊₁) > 1. Pair the bins up (1 with 2, 3 with 4, …): if NF uses m bins, there are ⌊m/2⌋ disjoint pairs, each holding more than 1. So Σ sᵢ > ⌊m/2⌋ ≥ (m − 1)/2. Since OPT ≥ Σ sᵢ, we get m < 2·OPT + 1, i.e. m ≤ 2·OPT.

The bound is tight: items 0.5, ε, 0.5, ε, … make NF use one bin per pair, about twice the optimum.

Randomized algorithms and randomized quicksort

A randomized algorithm flips coins while it runs. That can make bad inputs harmless, or trade a tiny, controllable chance of error for a big speed-up.

Why randomize?

  • No bad inputs: a deterministic algorithm has fixed worst-case inputs that an adversary (or plain bad luck, like already-sorted data) can supply. A randomized one makes the same input behave differently each run, so its expected time holds for every input.
  • Simplicity and speed: randomized algorithms are often much simpler than the best deterministic ones (primality testing, hashing, min-cut).

A Monte Carlo algorithm with one-sided error is never wrong on one kind of answer (say a "composite" verdict from a primality test is always right) and is wrong on the other kind with probability at most p. Run it t times independently: it is fooled every time with probability only pᵗ. A Las Vegas algorithm cannot be "amplified" this way because it never errs. Running it longer only changes how long it takes, not whether it is right.

Randomized quicksort

Plain quicksort with the last element as pivot takes Θ(n²) on sorted input, because every split is 0 versus n − 1. Picking the pivot uniformly at random makes such lopsided splits unlikely on any input.

RANDOMIZED-QUICKSORT(A, p, r):
    if p < r:
        q = RANDOMIZED-PARTITION(A, p, r)
        RANDOMIZED-QUICKSORT(A, p, q − 1)
        RANDOMIZED-QUICKSORT(A, q + 1, r)

RANDOMIZED-PARTITION(A, p, r):
    i = RANDOM(p, r)             // uniform random index
    exchange A[r] with A[i]      // move the pivot to the end
    return PARTITION(A, p, r)

PARTITION(A, p, r):              // Lomuto scheme, pivot x = A[r]
    x = A[r];  i = p − 1
    for j = p to r − 1:
        if A[j] ≤ x:
            i = i + 1;  exchange A[i] with A[j]
    exchange A[i + 1] with A[r]
    return i + 1

After PARTITION, everything left of position q is ≤ the pivot and everything right of it is larger. The pivot is in its final place.

4. Complexity Classes & Reduction Chains

Definitions for KTU PCCST502 Part A
  • P: Decision problems solvable in polynomial time O(nk) by a deterministic Turing machine.
  • NP: Decision problems verifiable in polynomial time by a deterministic Turing machine (or solvable in polynomial time by a non-deterministic machine).
