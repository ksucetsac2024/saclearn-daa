Branch and bound, and the travelling salesman

Like backtracking, branch and bound searches a state space tree. Each node also gets a lower bound on the cost of any solution below it, and the search always expands the most promising node next. Subtrees that cannot beat the best answer so far are cut off.

LC search and the cost function

Every node X gets an estimate ĉ(X) of the cost of the best answer in its subtree. For minimisation, ĉ is a lower bound: no solution below X can cost less than ĉ(X). Least-cost (LC) search always picks the live node with the smallest ĉ as the next E-node.

Control abstraction (LC search)

Algorithm LCSearch(t)          // t = root of the state space tree
{
    if t is an answer node then { output t; return; }
    E := t;                              // E-node
    initialise the list of live nodes to be empty;
    repeat
    {
        for each child x of E do
        {
            if x is an answer node then { output path from x to t; return; }
            Add(x);                       // x becomes a live node
            (x → parent) := E;            // to rebuild the path
        }
        if there are no more live nodes then { write ("No answer node"); return; }
        E := Least();                     // remove the live node with smallest ĉ
    } until (false);
}

With a FIFO queue in place of Least() it becomes FIFO branch and bound; with a stack, LIFO branch and bound. For optimisation problems, a common refinement: stop when the node chosen by Least() is itself a complete solution, because every other live node has ĉ at least as large.

TSP with reduced cost matrices

Find the cheapest tour that starts at city 1, visits every city exactly once and returns to 1. The cost matrix A has A[i][j] = cost of going from i to j, and ∞ on the diagonal.

Step 1: reduce the matrix to get a lower bound

Every tour leaves each city exactly once, so it must pay at least the cheapest entry of each row. Subtract each row's minimum from that row. Every tour also enters each city once, so then subtract each column's minimum from that column. Let r = the total subtracted. Every tour costs at least r, so r is a lower bound, and the root gets ĉ(root) = r. A matrix is reduced when every row and column has a 0 (or is all ∞).

Step 2: branching on an edge (i, j)

A child S of node R means "the tour goes from i to j next". Starting from R's reduced matrix A:

  1. Set every entry of row i to ∞ (we have already left i).
  2. Set every entry of column j to ∞ (we have already entered j).
  3. Set A[j][1] = ∞ (do not return to the start before the tour is complete).
  4. Reduce the result again; call the amount subtracted r.
Cost of the child
ĉ(S) = ĉ(R) + A(i, j) + r

A(i, j) is the entry in the parent's reduced matrix: the extra cost of actually using that edge.

Child for edge 1 → 5 from the root above

A(1,5) = 0. Blank row 1, column 5, and A[5][1]. Rows 2, 3, 5 already contain a 0; row 4 becomes (9, 3, 1, ∞, ∞) with minimum 1. After that, column 1 holds (4, 1, 8, ∞) with minimum 1. So r = 1 + 1 = 2, and ĉ = 28 + 0 + 2 = 30.

LC search then repeatedly expands the live node with the least ĉ. When the node it picks is a complete tour (a leaf), that tour is optimal: every other live node has a lower bound at least as high.

Subtracting a constant from a whole row lowers every tour by exactly that constant, so the order of tours is unchanged and r is paid by all of them.

Tractable and intractable problems: P, NP, NP-hard, NP-complete

Some problems have fast algorithms; for others, nobody has found one in fifty years of trying. Complexity classes sort problems by how hard they are, and reductions let us compare the hardness of two problems.

Tractable vs intractable

A problem is tractable if some algorithm solves it in polynomial time, O(nᵏ) for a constant k (sorting n log n, shortest paths, MST). It is intractable if no polynomial algorithm exists, or none is known, and the best algorithms are exponential (2ⁿ, n!). The line is drawn at polynomial because polynomials stay manageable as n grows and are closed under composition, while 2ⁿ doubles with every extra input item.

Decision vs optimisation problems

Optimisation problem

Asks for the best value. "What is the cheapest tour?" "What is the largest clique?"

Decision problem

Has a yes/no answer. "Is there a tour of cost ≤ k?" "Is there a clique of size ≥ k?"

Complexity classes are defined for decision problems. That loses nothing important: if the decision version is hard, the optimisation version is at least as hard (solving the optimisation answers the decision immediately). Conversely, a decision algorithm plus binary search on k usually finds the optimum.

The classes

P

Decision problems solvable in polynomial time by a deterministic algorithm. Examples: sorting, MST, shortest path, "is there a path from u to v?"

NP

Decision problems whose yes-answers can be verified in polynomial time, given a certificate (a proposed solution). Equivalently: solvable in polynomial time by a nondeterministic machine that "guesses" the certificate. NP means nondeterministic polynomial, not "not polynomial".

NP-hard

Problems at least as hard as every problem in NP: every NP problem reduces to it in polynomial time. An NP-hard problem need not be in NP, and need not even be a decision problem.

NP-complete

Problems that are both in NP and NP-hard: the hardest problems inside NP. Examples: SAT, 3-CNF-SAT, CLIQUE, VERTEX-COVER, decision TSP, Hamiltonian cycle, subset sum.

Certificates: how to show a problem is in NP

Describe the certificate and a polynomial-time check. Decision TSP ("tour of cost ≤ k?"): the certificate is the order of cities. Check it visits each city exactly once (O(n)), add up the n edge costs and compare with k (O(n)). That is polynomial, so decision TSP ∈ NP.

Every problem in P is also in NP (the verifier can just solve the problem itself and ignore the certificate), so P ⊆ NP. Whether P = NP is the most famous open question in computer science. Almost everyone believes P ≠ NP.

NP-hard but not NP-complete: the halting problem ("does program M stop on input x?") is NP-hard (SAT reduces to it: build a program that tries every assignment and halts if one satisfies the formula), but it is undecidable, so it is certainly not in NP. Optimisation TSP ("find the cheapest tour") is NP-hard but is not a decision problem, so it is not in NP either.

Polynomial-time reductions

A reduction from problem A to problem B, written A ≤ₚ B, is a polynomial-time function f that turns any instance x of A into an instance f(x) of B such that x is a yes-instance of A ⇔ f(x) is a yes-instance of B.

So if B is easy, A is easy too: transform, then solve B. Read the other way: if A is hard, B must be at least as hard. This is how hardness spreads from one problem to the next.

Recipe to prove a problem X is NP-complete

1. Show X ∈ NP: give a certificate and a polynomial-time verifier.

2. Pick a known NP-complete problem Y and show Y ≤ₚ X: build f, show it runs in polynomial time, and prove both directions of "x yes ⇔ f(x) yes".

Because ≤ₚ is transitive, every NP problem then reduces to X. The first NP-complete problem, SAT, was proved directly (Cook–Levin theorem).

If any NP-complete problem is in P, then P = NP

Let X be NP-complete with a polynomial algorithm. Take any problem L in NP. Since X is NP-hard, L ≤ₚ X: transform L's input in polynomial time, then run X's polynomial algorithm. A polynomial of a polynomial is still a polynomial, so L ∈ P. That holds for every L in NP, so NP ⊆ P, and with P ⊆ NP, P = NP.

Quick check

What does "NP" stand for?

Many NP problems (all of P, for instance) are solvable in polynomial time.

You prove 3-CNF-SAT ≤ₚ X. What follows?

Hardness travels along the reduction. To be NP-complete, X must also be shown to be in NP.

Which is in NP but believed to be outside P?

CLIQUE is NP-complete. Sorting and shortest path are in P; the halting problem is not in NP at all.

NP-completeness proofs: Clique and Vertex Cover

Two complete examples of the recipe: prove the problem is in NP, then reduce a known NP-complete problem to it.

Definitions

Clique

A clique in an undirected graph is a set of vertices that are all pairwise adjacent (a complete subgraph). CLIQUE = {⟨G, k⟩ : G has a clique of size k}.

Vertex cover

A vertex cover is a set of vertices that touches every edge: each edge has at least one endpoint in the set. VERTEX-COVER = {⟨G, k⟩ : G has a vertex cover of size k}.

3-CNF-SAT

A Boolean formula that is an AND of clauses, each clause an OR of exactly 3 literals (a variable or its negation). Is there an assignment making it true? Known NP-complete.

CLIQUE is NP-complete

Part 1: CLIQUE ∈ NP

Certificate: the set V′ of k vertices. Verifier: check |V′| = k, then check every pair u, v ∈ V′ is an edge. That is k(k−1)/2 ≤ |V|² edge checks, polynomial. So CLIQUE ∈ NP.

Part 2: 3-CNF-SAT ≤ₚ CLIQUE

Given a formula φ = C₁ ∧ C₂ ∧ … ∧ Cₖ with k clauses, build a graph G:

  1. For each clause Cr = (l₁ ∨ l₂ ∨ l₃), create 3 vertices, one per literal.
  2. Connect two vertices by an edge if (a) they come from different clauses, and (b) their literals are not complements of each other (not x and ¬x).
  3. Ask for a clique of size k (the number of clauses).

G has 3k vertices and at most 9k² edges, so it is built in polynomial time.

Proof of correctness (both directions)

(⇒) φ satisfiable ⇒ G has a k-clique. Take a satisfying assignment. Each clause has at least one true literal; pick one vertex for such a literal from every clause: k vertices. Any two of them are from different clauses, and both literals are true, so they cannot be x and ¬x. Hence every pair is joined by an edge: a k-clique.

(⇐) G has a k-clique ⇒ φ satisfiable. Vertices of the same clause are never adjacent, so a k-clique has exactly one vertex per clause. No two of its literals are complementary (they are all adjacent), so we can set every one of them true without conflict. Variables not mentioned can be anything. Each clause then has a true literal, so φ is satisfied.

VERTEX-COVER is NP-complete

The key fact: cliques and covers are complements

The complement graph Ḡ has the same vertices as G, and an edge exactly where G does not have one.

G has a clique of size k ⇔ Ḡ has a vertex cover of size |V| − k

(⇒) Let V′ be a clique in G. Take any edge (u, v) of Ḡ. Then (u, v) is not an edge of G, so u and v are not both in V′ (all pairs inside V′ are G-edges). So at least one of u, v is in V − V′: the set V − V′ covers every edge of Ḡ, and its size is |V| − k.

(⇐) Let V − V′ be a vertex cover of Ḡ. Take any u, v both in V′. If (u, v) were an edge of Ḡ, the cover V − V′ would have to contain u or v, but neither is in it. So (u, v) is not in Ḡ, i.e. it is an edge of G. Every pair in V′ is adjacent in G: V′ is a clique of size k.

The proof

  1. VERTEX-COVER ∈ NP. Certificate: the set V′ of k vertices. Check |V′| = k, then for every edge (u, v) check u ∈ V′ or v ∈ V′: O(V + E). Polynomial.
  2. CLIQUE ≤ₚ VERTEX-COVER. Given ⟨G, k⟩, output ⟨Ḡ, |V| − k⟩. Building Ḡ takes O(V²). By the fact above, G has a k-clique exactly when Ḡ has a vertex cover of size |V| − k.

CLIQUE is NP-complete, so VERTEX-COVER is NP-hard, and being in NP it is NP-complete.

Approximation algorithms: bin packing

For NP-hard optimisation problems we often give up on the exact optimum and accept a fast algorithm with a proven guarantee: "never more than twice the optimum", for example.

Approximation ratio

An algorithm has approximation ratio ρ(n) if, for every input of size n, its answer C and the optimum C* satisfy

max( C / C*, C* / C ) ≤ ρ(n)

For minimisation that means C ≤ ρ·C*; for maximisation, C ≥ C*/ρ. A ρ-approximation algorithm always runs in polynomial time. ρ = 1 would mean exact.

The bin packing problem

Given n items with sizes s₁, …, sₙ, each 0 < sᵢ ≤ 1, pack them into the fewest bins of capacity 1. It is NP-hard. One easy lower bound: the items' total size must fit, so OPT ≥ ⌈Σ sᵢ⌉.

Next Fit (NF)

Keep only the current bin open. If the item fits, put it in; otherwise close the bin forever and open a new one. O(n).

First Fit (FF)

Put the item into the first (lowest-numbered) bin with enough room; open a new bin only if none has room. O(n²) simply, O(n log n) with a tree.

Best Fit (BF)

Put the item into the bin where it fits most tightly (least room left afterwards). Ties go to the lowest-numbered bin.

First Fit Decreasing (FFD)

Sort items largest first, then run First Fit. Best Fit Decreasing (BFD) is the same idea with Best Fit. Sorting puts big awkward items in early, leaving small ones to fill the gaps.

Why Next Fit never uses more than 2·OPT bins

Look at any two consecutive bins Bᵢ and Bᵢ₊₁ in NF's packing. NF opened Bᵢ₊₁ because the next item did not fit in Bᵢ, so (contents of Bᵢ) + (contents of Bᵢ₊₁) > 1. Pair the bins up (1 with 2, 3 with 4, …): if NF uses m bins, there are ⌊m/2⌋ disjoint pairs, each holding more than 1. So Σ sᵢ > ⌊m/2⌋ ≥ (m − 1)/2. Since OPT ≥ Σ sᵢ, we get m < 2·OPT + 1, i.e. m ≤ 2·OPT.

The bound is tight: items 0.5, ε, 0.5, ε, … make NF use one bin per pair, about twice the optimum.

Randomized algorithms and randomized quicksort

A randomized algorithm flips coins while it runs. That can make bad inputs harmless, or trade a tiny, controllable chance of error for a big speed-up.

Why randomize?

  • No bad inputs: a deterministic algorithm has fixed worst-case inputs that an adversary (or plain bad luck, like already-sorted data) can supply. A randomized one makes the same input behave differently each run, so its expected time holds for every input.
  • Simplicity and speed: randomized algorithms are often much simpler than the best deterministic ones (primality testing, hashing, min-cut).

Las Vegas vs Monte Carlo

AnswerAlways correctCorrect with high probability; may be wrong
Running timeRandom; we bound the expected timeFixed (bounded) number of steps
ExampleRandomized quicksortMiller–Rabin primality test, Karger's min-cut
Improve byNothing to improve: the answer is already rightRepeating independent runs

A Monte Carlo algorithm with one-sided error is never wrong on one kind of answer (say a "composite" verdict from a primality test is always right) and is wrong on the other kind with probability at most p. Run it t times independently: it is fooled every time with probability only pᵗ. A Las Vegas algorithm cannot be "amplified" this way because it never errs. Running it longer only changes how long it takes, not whether it is right.

Randomized quicksort

Plain quicksort with the last element as pivot takes Θ(n²) on sorted input, because every split is 0 versus n − 1. Picking the pivot uniformly at random makes such lopsided splits unlikely on any input.

RANDOMIZED-QUICKSORT(A, p, r):
    if p < r:
        q = RANDOMIZED-PARTITION(A, p, r)
        RANDOMIZED-QUICKSORT(A, p, q − 1)
        RANDOMIZED-QUICKSORT(A, q + 1, r)

RANDOMIZED-PARTITION(A, p, r):
    i = RANDOM(p, r)             // uniform random index
    exchange A[r] with A[i]      // move the pivot to the end
    return PARTITION(A, p, r)

PARTITION(A, p, r):              // Lomuto scheme, pivot x = A[r]
    x = A[r];  i = p − 1
    for j = p to r − 1:
        if A[j] ≤ x:
            i = i + 1;  exchange A[i] with A[j]
    exchange A[i + 1] with A[r]
    return i + 1

After PARTITION, everything left of position q is ≤ the pivot and everything right of it is larger. The pivot is in its final place.

Expected running time: O(n log n)

All the work is comparisons inside PARTITION, so count the total number of comparisons X. Name the elements by sorted order: z₁ < z₂ < … < zₙ.

  1. Indicator variables. Let Xij = 1 if zᵢ and zⱼ are ever compared, else 0. Two elements are compared at most once (only against a pivot, and a pivot is never used again). So X = Σi<j Xij and, by linearity of expectation, E[X] = Σi<j Pr[zᵢ compared with zⱼ].
  2. When are zᵢ and zⱼ compared? Look at the set Zij = {zᵢ, zᵢ₊₁, …, zⱼ}, which has j − i + 1 elements. They stay together in one subarray until the first pivot chosen from Zij. If that pivot is zᵢ or zⱼ, the two are compared. If it is something in between, they are split into different sides and never meet.
  3. The probability. Every element of Zij is equally likely to be that first pivot, so Pr[compared] = 2 / (j − i + 1).
  4. Add up. Put k = j − i:
    E[X] = Σᵢ Σⱼ>ᵢ 2/(j − i + 1) = Σᵢ Σₖ₌₁..ₙ₋ᵢ 2/(k + 1) < Σᵢ₌₁..ₙ Σₖ₌₁..ₙ 2/k = n · 2Hₙ = O(n log n) (Hₙ ≈ ln n)

Nothing in this argument depends on the input order, only on the random pivot choices. So the expected time is O(n log n) for every input, including sorted ones. The worst case is still Θ(n²) (if the random choices are terrible every time), but that is extremely unlikely. Randomized quicksort is a Las Vegas algorithm: the output is always correctly sorted; only the time varies.
